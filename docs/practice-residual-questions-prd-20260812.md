## 1. 业务目标

错题小老师 V4 定位为**可商业落地的 AI 数学教练**，练习页（/practice）是核心付费体验入口。当前用户抽到的选择题存在「残缺题」——仅 A/B/C 三选项、缺 D，前端以灰色 disabled 显示「做完不算分」，直接损害「做题—评分—讲解」闭环的可信度，是商业交付的硬伤。本 PRD 目标：**在抽题数据层彻底消除残缺选择题**——能可靠补齐 D 选项的补齐，无法可靠补齐（OCR 损坏 / 逻辑错误）的直接 archive 下架；同时建立入库卡口，杜绝后续新增残缺题。最终让用户在 /practice **永远看不到**任何残缺题或「做完不算分」的兜底 UI。

## 2. 用户故事

**主用户故事（学生 / 付费用户）**
> 作为在 /practice 刷题的小学生，我希望抽到的每道选择题都有完整 A/B/C/D 四个选项且能正常计分，以便我能顺畅完成练习并获得准确反馈，而不是面对「做完不算分」的残缺题产生困惑与失望。

**扩展用户故事 1（家长 / 付费决策者）**
> 作为付费家长，我希望练习题库中不存在因缺选项而无法评分的题目，以便相信产品的专业度、愿意持续续费。

**扩展用户故事 2（内容运营 / 维护者）**
> 作为题库维护者，我希望新题入库时自动拦截残缺题（缺选项即失败），以便残缺题不会再次流入线上，降低长期运维成本。

## 3. 需求池（P0 / P1 / P2）

### P0（必须做）

**N0.1 — 4 道截图题立即修复**（按主理人已定位的 UUID 与处置标注）

| UUID（前缀） | 题干摘要 | 现状（A/B/C） | 处置 | 补 D / 备注 |
|---|---|---|---|---|
| `9a4f1461-...` | 比 40 大、比 60 小、个位是 5 的数 | 缺 D（A=50, B=55, C=35） | **补 D** | D=65（个位是 5 但 >60，易错干扰项）；正确 = B |
| `9cf5259e-...` | 要使 1□6 ÷ 6 得数是一位数，□最大填 | 缺 D（A=7, B=6, C=5） | **archive** | 逻辑本身错误（三位数 ÷6 商不可能是一位数）+ OCR 把「÷」误读成「-」，无法可靠补 |
| `a3275f03-...` | 小阳 28 张，小强比小阳多得多…可能有几张 | 缺 D（A=12, B=32, C=63） | **补 D** | D=30（多一点点但不够「多得多」）；正确 = C |
| `855ae9b6-...` | 妈妈和奶奶共做 13 个包子…奶奶做了几个 | 缺 D（A=13-4, B=13-5-4, C=13-5） | **补 D** | D=5-4（只算肉包数，典型干扰）；正确 = C |

- **执行口径**：3 道补 D（保留原 A/B/C 内容与顺序，仅追加 D 键，correct_answer 指向不变）；1 道 archive（status 置 `archived`，移出抽题池）。
- **验收**：4 题处理完毕，/practice 抽样不再出现这 4 题的残缺态。

**N0.2 — 全库 312 道残缺选择题批量处置**
（建议策略：**混合「AI 辅助补 D + 人工抽审」+ 不可补则直接 archive**）

- **现状**（主理人已查实）：312 道残缺选择题跨 1~6 年级，按 (grade, difficulty) 散落；全部缺 D（少数题型缺 A/B/C）；其中 9 道含除法符号（÷），存在 OCR 误差风险。
- **推荐策略（不建议全量 archive，也不建议纯人工逐题补）**：
  1. **先分类**：对 312 题逐条判定「可补 / 不可补」。
     - *可补*：题干与 A/B/C 语义连贯、仅缺 D → 进入补 D 流程。
     - *不可补*：含 OCR 损坏（如 ÷→-）、题干逻辑自相矛盾、或缺 A/B/C 无法还原 → 直接 `archive`。预计 9 道除法符号题大概率属此类（需人工确认），其余多数属「可补」。
  2. **AI 辅助批量补 D**（执行细节归高见远，本 PRD 仅定口径）：对「可补」题，由 AI 基于同年级知识点生成 1 个 plausible 干扰项 D，约束为 D 与原 A/B/C 不重复、且**不改变**原 correct_answer；高置信度自动应用，低置信度打 `needs_review` 标记转人工。
  3. **人工抽审**：对 AI 补 D 结果按年级分层抽样复核（如每年级抽 10%），确认 D 不引发「多解 / 歧义」后全量生效。
  4. **archive 清单留痕**：所有 archive 题写入删除清单 CSV（见第 5 节待确认问题 3），含 UUID 与原因。
- **决策理由**：纯 archive 会一次性损失 312 道可用题、削弱题库覆盖度（商业产品伤不起）；纯人工逐题补成本过高且不可规模化；混合策略在「保题库价值」与「控质量风险」间取得平衡。

### P1（应该做）— 防止新增残缺题

- **P1.1 入库校验卡口**：新题导入（importer / docx 解析 / 人工录入）时，**选择题必须含完整 A-D 选项且 correct_answer 命中其一**，否则导入失败或置 `status=draft` 进入待审，禁止直接 `published`。
- **P1.2 CI / 数据质量门禁**：在既有 `test_data_cleanliness`（如 `test_no_choice_question_with_missing_options`）基础上，将「选择题 options 键数 < 4（A-D 缺失）即断言失败」纳入 CI 常驻校验，阻断带残缺题的发布。
- **P1.3 人工抽审机制**：新增题库内容由运营按批次抽样复核，重点检查 OCR 高风险题（含 ÷、分数、对齐表格等）。

### P2（可以做）— 前端 disabled 兜底降级

- **P2.1 移除用户可见的「做完不算分」disabled 卡**：P0/P1 完成后，库内已无残缺题，正常路径下不应再渲染残缺卡片。将前端对「选项不完整」的展示从「灰色 disabled + 提示文案」改为**服务端直接过滤**（抽题 API 排除 `archived`，只返回完整题）。
- **P2.2 保留后端静默守卫**：若极端情况下残缺题仍到达 session，服务端**不**向用户展示破损 UI，而是自动将其排除出计分、并触发**日志 / 运维告警**（而非 UI 兜底），供后续排查。即「UI 兜底 → 日志告警」降级。

## 4. UI / 验收标准

1. **用户侧零残缺**：在 /practice 任意次数抽题，返回的选择题**均含完整 A/B/C/D 四个选项**，且**永不出现**灰色 disabled「做完不算分」的兜底卡片。
2. **数据层可验证**：全库所有 `status='published'` 的选择题，`options` 经归一化后**键数 == 4 且含 A/B/C/D**；等价校验——以 `options LIKE '%"D"%'` 为条件的查询，命中数 == 全库选择题总数（残缺数归零）。
3. **截图 4 题达标**：`9a4f1461 / a3275f03 / 855ae9b6` 三题 D 选项已补齐且 correct_answer 不变；`9cf5259e` 已 `archived`、不再进入抽题池。
4. **入库卡口生效**（P1）：构造一道缺 D 的测试选择题导入，系统**拒绝**其进入 `published`（失败或转 `draft`）；CI 中 `test_no_choice_question_with_missing_options` 全绿。
5. **回归**：复用 `practice-module-redesign-prd` 既有 `TestDataCleanlinessOnRealBank` 用例，确认「选项缺失 / 题干污染 / kp_id 空」三类问题全库为 0。

## 5. 待确认问题（请主理人决策）

1. **不可补题的处置粒度**：312 题中确有 OCR 截断 / 逻辑损坏（如第 2 题）而无法可靠补 D 的题，是直接 `archive` 永久下架，还是保留一个 `needs_review`（待人工补）的 flag 暂不销毁？——建议：直接 archive 并留 CSV 清单（可恢复），但不阻塞发布。
2. **补 D 后选项顺序**：补 D 时是否严格保留原 A/B/C 顺序（D 永远追加在末位），还是按数值 / 逻辑重排四选项？——建议：保留原 A/B/C 顺序，D 追加末位，避免改动已验证的 correct_answer 指向。
3. **删除清单 CSV 是否必须**：是否要求为本次所有 archive 题导出一份 `residual-questions-20260812.csv`（含 UUID、原因、原 grade/difficulty），便于事后复核与恢复？——**建议必须**，格式对齐既有 `removed-questions-20260812.csv`（`question_id,old_status,old_kp_id,reason,removed_at`），并新增 `new_options` 列记录补 D 结果。
4. **选择题标准选项数**：验收以「完整 A-D（4 项）」为准，还是允许部分低龄题合法为 3 项？——影响验收门槛，需确认题库是否存在「合法的 3 选项题」。
5. **P2 前端兜底是否本期删**：P2 的「移除 disabled UI」是否纳入本期，还是仅先做 P0/P1 数据治理、前端兜底留作长期防御？——建议本期即删用户可见兜底，保留后端日志告警。
