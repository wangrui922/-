## 1. 增量目标

### 1.1 为什么做（Why now）

产品核心闭环是「错题诊断 → 薄弱点 → 定向练习」。当前题库仅 **909 题**，且全部来自旧 `index.html` 抽取，存在两个硬缺口：

| 缺口 | 现状 | 影响 |
|---|---|---|
| **题量与覆盖不足** | 909 题，知识点仅 7 个粗类（计算/方程/应用题/分数/图形/几何/综合） | 定向练习易重复出题，学生刷到重题，闭环体感差 |
| **无教材版本概念** | `questions` 表无 `edition` 字段 | 青岛版学生可能刷到苏教版题，教学进度错位 |
| **无期末/衔接场景题** | 现有题无场景标签 | 无法支撑「暑假衔接」「期末冲刺」这类高价值使用场景 |

登记在册的 15 个 docx（青岛版衔接 5 册 + 苏教版期末 10 份）是**已到手、零采购成本**的优质种子，不入库就是浪费。

### 1.2 做完达到什么（Definition of Done）

| 目标 | 可度量标准 |
|---|---|
| **G1 题目结构化入库** | 15 个源 docx 全部解析完成，新增题目落入 `questions` + `answers`，导入成功率 ≥ 90%（按识别出的题块计） |
| **G2 答案可用** | 新增题目中 `answers.correct_answer` 非空占比 ≥ 85%（青岛版同册答案 + 苏教版配对答案）；`analysis` 允许空 |
| **G3 多版本隔离** | 任意查询可通过 `edition` 精确筛出「青岛版」或「苏教版」题目，两者互不串（决策③） |
| **G4 知识点闭环可跑** | 每题带 `kp_id`(可空) + `kp_verified`(默认 false)；`kp_verified=false` 的题目**不进入薄弱点统计**（决策②） |
| **G5 可重复执行** | 导入脚本重跑 N 次，`questions` 总数不变（幂等），不产生重复题 |
| **G6 不污染现有资产** | 存量 909 题的 `edition`/`kp_verified` 有明确兜底值；`pytest` 既有用例零回归 |

### 1.3 明确不做（Non-Goals）

| 不做项 | 理由 |
|---|---|
| AI 出题 / 练习生成逻辑 | `backend/app/ai/agents/exercise.py` 已存在并在线运行，本期**复用，零改动** |
| 学生端练习 UI | 复用现有 `student-web` 页面，本期无前端新增页面 |
| docx 原文件入 git | 单册 5~7MB，合计 ~37MB，会撑爆仓库（manifest §5.4 已明令） |
| 图片/公式题的图像提取 | docx 内嵌图片本期不落 `image_url`，纯文本题优先（见 §6 待确认 U5） |
| 知识点体系扩容（7 类 → 细粒度） | 本期沿用现有 7 个粗类打标；细化知识图谱是独立议题 |
| 人教版王朝霞 5 册 / 未标版本的专项卷 15 份 | manifest §A.5 已列排除清单 |

## 5. 数据映射要点

### 5.0 ⚠️ 先纠偏：任务书字段名 ≠ 代码真实字段名

我核对了 `backend/app/models/content.py`（真实 ORM）与 `docs/v4-db-api.md`（设计稿），发现**任务书中给出的字段清单与仓库现状有 6 处不符**。以下**以真实代码为准**，工程师请勿照抄任务书字段名。

| # | 任务书写法 | 仓库真实情况 | 处置 |
|---|---|---|---|
| **M1** | `stem`（题干） | 字段名是 **`questions.content`** | 用 `content`，**不要新增 `stem` 列** |
| **M2** | `answer` / `analysis` 挂在 `questions` 上 | 是**独立的 `answers` 表**（1:1，`question_id` UNIQUE），字段为 `correct_answer` / `analysis` | 每题写 2 行（1 行 `questions` + 1 行 `answers`），**不要把答案塞进 questions** |
| **M3** | `knowledge_point_id` | 字段名是 **`questions.kp_id`**（已存在，`nullable=True`，FK→`knowledge_points.id`） | 直接复用，**无需改可空性**（注意：`v4-db-api.md` 写的 NOT NULL 是过时设计稿，代码里是可空的） |
| **M4** | `grade_from` / `grade_to` | 真实表只有**单个 `grade`**（SmallInteger, nullable） | 见 §5.2 年级映射策略，**不新增两列** |
| **M5** | `type`(口算/填空/选择/应用/图形) | 真实 `questions.type_` 映射列名 `type`，约定枚举 `QUESTION_TYPE_VALUES = ("选择","填空","应用","计算")` —— **只有 4 类，无「口算」「图形」** | 见 §5.3 题型收敛表（注：DB 层无 CHECK 约束，仅代码常量约定，但仍应收敛以免污染） |
| **M6** | `edition`/`source_type`/`section`/`source_doc`/`kp_verified` | **全库 grep 零命中，5 个字段均不存在** | 本期需新增 5 列（R-05），配 PG + SQLite 双方言迁移 |

#### 为什么 C 不是"准确率优化"，而是可行性前提

自动打标最容易被误解成"锦上添花的准确率问题"，实际它改变的是**人工复核的性质**：

| | 人工复核要做什么 | 可行性 |
|---|---|---|
| **不打标**（现状 P2） | 从零标注 1000+ 题 | ❌ 几乎不可能完成 → `kp_verified` 永远 false → 闭环永远转不起来 |
| **打标后** | 只需**确认 / 纠正** | ✅ 单题秒级，可批量推进 → 闭环真能转 |

即：R-17 是让「`kp_verified=true`」这件事**从不可行变为可行**的前置条件，而不是让它"更准"。

**架构侧评估**（架构师给出）：`kp_tagger` hook 已预留，接入 **loader.py 零改动**；约 1 个新文件 60~100 行 + 一张关键词表；**零新增依赖**（纯关键词匹配，不调 AI）；安全性不变——打完仍 `kp_verified=false`，过滤开关是 `kp_verified` 而非 `kp_id`。

**落点**（🔴 已决策，见 v1.5.1 决策记录）：**R-17 自动打标（T6）本期不做，整体留给出题模块**。本模块最终任务集为 **T1~T5**，不补 T6。架构师已在设计 §8 登记为 **Q8**，并由 🔴 待决策转为 🟢 已决策；T1~T5 不受影响、可立即开工。本 PRD 此前把 R-17 标为「建议提 P1」的论证（B+C、可行性前提、推荐侧闸门绑定）**全部保留为出题模块的接手依据**，不在本模块落地。

#### 🔴 架构师 v1.4 追加确认：推荐链路缺 `kp_verified` 闸门，进一步坐实「T6 是激活一条休眠链路」

把 U8 的论证再往前推一层——前面说的"闸门后面没有水"是**掌握度引擎侧**（U7 归因置空）。v1.4 用同一张「机制叠加」检查表过 `profile_service` 的每一处 `Question.kp_id`，发现了**第四处**，落在**定向推荐链路**：

`profile_service.py:737-738` 的 `_suggested_questions()` 按 `Question.kp_id.in_(targets)` 匹配学生薄弱点推题，但**只过滤 `status == "active"`，不过滤 `kp_verified`**。

| 阶段 | 有没有问题 |
|---|---|
| **本期**（R-17 未做，`kp_id` 全 NULL） | ✅ 无问题。`kp_id.in_(targets)` 不命中 NULL → 新题天然进不了定向推荐 |
| **T6 落地后**（`kp_id` 被 best-effort 填上） | 🔴 立刻出问题 |

T6 落地后的机制叠加：

| | 机制 | 单看 |
|---|---|---|
| A | T6 自动打标给新题填 `kp_id`（best-effort，**可能打错**） | ✅ |

- 它证明 R-17 提 P1 **不是"多做一个功能"**，而是会**激活一条目前休眠、且当前没有任何闸门的链路**。一旦打标有输出，就会立刻流进推荐，而推荐侧此刻没有 `kp_verified` 闸门兜底。
- 因此 T6 的落地必须同期处理"未复核题能否进入定向推荐"——已登记为 **T6 前置约束**，本期（`kp_id` 全 NULL）**无需任何改动**：
  - **选项①（保守）**：`_suggested_questions()` 加 `kp_verified == True` 过滤 → 新题需复核后才被定向推荐（与 U7 的闸门口径一致，是推荐侧的对称设计）；
  - **选项②（激进）**：不过滤，靠 U2 抽检兜底 → 打标错误会直接影响推荐精准度，存在"教错题/推偏"的体验风险。
- 与 U7（掌握度侧闸门）合起来看：**`kp_verified` 必须成为"凡是消费 `kp_id` 的链路"的统一前置**，掌握度引擎和推荐引擎两处都得过闸。

> 一句话给主理人：**U8 现在不只是"闭环保不保得全"，而是"一旦要做 C（R-17 提 P1），就必须把推荐侧这道闸门一起补上"——两个决策绑死，不能只做一个。**

> 📌 **v1.5.1 决策更新（重要，给出题模块接手时看）**：经主理人拍板，**R-17 自动打标（T6）本期不在本模块交付范围，整体留待出题模块落地**。上述「T6 前置约束 / 推荐侧 `kp_verified` 闸门绑定」的论证**不是本模块漏做**，而是有意识地推迟到出题模块——本模块 T1~T5 交付后，出题模块接手时可直接复用这里的约束清单（打标器 + 推荐侧 `kp_verified` 闸门 + 掌握度侧 U7 闸门 + 运营决策保留 R-23，四件绑死）。本 PRD 的论证因此**全部转为出题模块的接手依据**，与 §7.4「本期不做」口径一致。

### 7.1 🔴 为什么 V8 必须拆成 a/b/c 三条（我原验收口径的漏洞）

我原先只写了「造一条**错误**作答 → mastery 不受影响」。架构师指出 `kp_verified` 的隔离需在 `profile_service` **两处成对替换**，我核实代码后确认——**我原来那条验收会漏掉更危险的那个 bug**：

| 代码路径 | 位置 | 喂给掌握度的样本 |
|---|---|---|
| **作答路径** `_load_attempts()` | `profile_service.py:272-291`，JOIN 取 `Question.kp_id` | 正样本 **+ 负样本**（`is_correct` 直接来自 attempt） |
| **错题路径** `_question_kp_map()` | `profile_service.py:187-195`，被 `_load_mistakes()` L304 调用 | 负样本 + 「已攻克」正样本（L335-345） |

**只改一处的后果**：

| 改了哪处 | 后果 | 我原 V8 能否发现 |
|---|---|---|
| 只改 `_load_attempts()` | 错题路径仍归因 → 未复核题的错题照样污染掌握度，R-07 形同虚设 | ✅ 能发现 |
| **只改 `_question_kp_map()`** | 作答路径仍归因 → 未复核题的**正确作答**变成正样本 → **掌握度被虚高拉升**（比不改更危险：系统会误判学生已掌握，进而停止推送该知识点的练习） | ❌ **发现不了** |

因为我原来的用例只造「错误作答」，走的是错题路径；而虚高拉升由**正确作答**经作答路径造成。故必须补 **V8-b**（正确作答不得拉升掌握度）。V8-c 则用于证明隔离是"可逆开关"而非"永久丢弃"——复核通过后数据要能回到统计里，否则决策②的"待复核"就成了单向丢弃。

### 7.2 🔴 V8-c 的隐藏前提：掌握度是物化缓存，翻 `kp_verified` 不会让它失效

架构师核查发现，V8-c **在当前实现下会挂**。我实读代码确认：`profile_service.py:362-385` 的 `_is_cache_valid()` 只认两个失效条件——

1. `computed_at + TTL > now`（TTL = `MASTERY_CACHE_TTL_SECONDS` = **900 秒**）
2. `last_practiced_at <= computed_at`（算完之后有没有新的**练习/攻克**）

**两条都只感知「练习行为」，感知不到「元数据变更」**。而 `kp_verified` 翻转恰恰是一次纯元数据变更：

```
学生做了 10 道未复核题 → 掌握度缓存算过一次（这 10 次不计入）
→ 运营翻 kp_verified = true（不产生任何练习事件）
→ last_practiced_at 不动、computed_at 未过期 → 缓存判定有效
⇒ get_mastery() 返回旧缓存，那 10 次作答 15 分钟内「回不来」
```

**产品要求**：复核动作必须**立即**在掌握度上体现，不能"最终一致"。理由是复核方的工作流就是「确认 → 检查生效了没」，15 分钟的静默期会让人以为复核没成功而重复操作，或误报 bug。

**解法**（架构师已并入 T4 第 ⑦ 项）：`promote_bank.py --mark-verified` 两步走——① `UPDATE kp_verified=true`；② 反查受影响的 `(student_id, kp_id)` 并调 `touch_mastery_practiced()` 推高 `last_practiced_at` 使缓存失效。

#### 由此产生的两条硬性运维约定

| # | 约定 | 违反后果 |
|---|---|---|
| **OPS-1** | **翻 `kp_verified` 一律走 `--mark-verified`，禁止手搓 `UPDATE`** | 只 UPDATE 不失效缓存 → 「复核完了掌握度纹丝不动」→ 极易被当成 bug 排查半天。⚠️ 注意设计 §4.4 给 `status` 上架提供了「等价 SQL」，**该模式不可套用到 `kp_verified`** |
| **OPS-2** | **V8-c 用例禁止使用 `get_mastery(force=True)`** | 用 `force` 会绕过缓存直达算法层 → **测试通过但没测到真正的坑**。这与「原 V8 会给半吊子改法发绿灯」是同一类问题：**验收方式本身决定了能不能抓到 bug** |
| **OPS-3** | **`--reset-bank` 只能清理"从未被练习过"的题** | 否则会连带删除学生的作答/错题/辅导记录，且不可逆。见 §7.3 |
| **OPS-4** | **落库 upsert 一律走 `on_conflict_do_update`（PK 保留式）** | 用「按 stable_key 删旧行再插新行 / `bulk_delete+bulk_insert` / `session.delete()+add()`」实现幂等，会点燃 `delete-orphan` 级联，**当场抹掉学生作答/错题/辅导记录**（同 R-21 级，且无人值守），见 §7.4 R-22 |
| **OPS-5** | **`on_conflict_do_update` 的 `set_` 只含源派生列，且禁用 `session.merge(全字段)`** | `merge` 会把它拷回所有标量列，把已上架题静默降级回 `archived`、把已复核题取消复核（并再触发 §7.2 缓存前提空洞）→ **运营决策无声撤销**，见 §7.4 R-23 |

### 7.3 🔴 `--reset-bank` 会 CASCADE 删掉学生的学习记录（机制叠加检查表发现）

沿用架构师"两个各自正确的机制叠起来产生空洞"的视角，我把本模块尚未交叉核对的机制对又过了一遍，发现这一处：

| | 机制 | 单看是否正确 |
|---|---|---|
| **A** | `--reset-bank` 按 `source_doc` 删题后重灌（架构师 Q5 建议：解析规则大改后先清后灌） | ✅ 合理，为迭代解析规则而设 |
| **B** | `Question` 到学习数据的级联删除 | ✅ 合理，标准引用完整性 |
| **A × B** | **重灌会摧毁学生学习历史** | 🔴 |

**代码证据**（已实读）：

| 层 | 关系 | 后果 |
|---|---|---|
| ORM `content.py:117-119` | `mistakes` / `attempts` / `ai_sessions` 均为 `cascade="all, delete-orphan"` | `session.delete(question)` → **三者一并删除** |
| DB `learning.py:52` | `mistakes.question_id` → `ondelete="CASCADE"` | 裸 SQL 删题 → **错题记录一并删除** |
| DB `learning.py:93` | `attempts.question_id` → `ondelete="SET NULL"` | 裸 SQL 删题 → 作答保留但**失去题目关联** |

**为什么危险**：
1. `attempts` 是掌握度的**唯一事实源**（Epic6 明确「画像由它重算」）。删掉 = 永久摧毁学习历史，无法重算；
2. **不可逆**，且**静默**——`--reset-bank` 的字面语义是"清理题目"，没人会预期它动学生数据；
3. 触发时机很自然：架构师 Q5 正是建议「解析规则大改后用 `--reset-bank` 先清后灌」。若此时部分题已上架并被练习，就中招。

**产品要求（R-21）**：`--reset-bank` 删除前必须逐题检查学习引用，**有引用的一律拒绝删除**并列入跳过清单。宁可留下少量孤儿题（可用 `status='archived'` 下架），也绝不能删学生数据。

> **顺带确认一个好消息**：我同时核对了「U2 归档闸门 × 推荐链路」这对——`profile_service.py:738` 的 `_suggested_questions()` **已经带了 `Question.status == "active"` 过滤**。所以未上架的新题不会漏进推荐池，U2 的闸门（**status 维度**）是真实有效的，无需任何改动。

> ⚠️ **但同一行的"另一根轴"是 v1.4 新发现的缺口**：`_suggested_questions()` 只过滤 `status`、**不过滤 `kp_verified`**（见 §6.3 末尾"v1.4 追加确认"）。它今天安全，是因为 `kp_id` 全 NULL（`.in_(targets)` 不命中 NULL）；**T6 一旦落地，这就是必须补的闸门**——与 U8 的"R-17 提 P1 须配套决策"绑为同一件事。本期无需改动，已登记为 T6 前置约束。

### 7.4 🔴 重导入是第二个数据摧毁面：PK 保留式 + 只刷源列（v1.5 机制叠加续查）

沿用同一张「机制叠加」检查表再过一遍，又逮到 3 处（R-22 / R-23 / R-24），其中 R-22/R-23 与 R-21 同属「数据摧毁级」，根因同样藏在我自己写进文档的操作建议里。

#### R-22（P0）：upsert 必须是「PK 保留式」，严禁 delete+insert

| | 机制 | 单看是否正确 |
|---|---|---|
| A | 幂等重灌用 `uuid5(NS, 稳定键)` 派生主键 + upsert | ✅ 合理，重跑是覆盖而非新增 |
| B | `Question` → 学习数据 `cascade="all, delete-orphan"`（`content.py:117-119`） | ✅ 引用完整性标准做法 |
| **A × B** | 若 upsert 用「先删后插 / bulk_delete+bulk_insert」实现，每次重导入都会 `DELETE` 旧 `Question` 行 → 级联抹掉学生的 `attempts/mistakes/ai_sessions` | 🔴 数据摧毁级 |

**与 R-21 的关系**：R-21 只护住了 `--reset-bank` 这一条**显式删除**路径；而**日常导入 / 重导入**这条更常用的路径，若工程师为"求快"把 upsert 写成"按 stable_key 删旧行再插新行"，就会踩同一个雷，且没有任何 `RB1~RB3` 保护。

**产品要求（R-22 铁律）**：`loader.load()` 一律走 `Insert.on_conflict_do_update(index_elements=[Question.id], set_=源派生列)`（PG 与 SQLite ≥3.24 均支持），**严禁** `session.delete()+add()`、**严禁** `bulk_delete+bulk_insert`、**严禁** 按 `stable_key` 反查 id 后删行。理由：`on_conflict_do_update`/`merge()` 命中同 PK 发 UPDATE，不触碰关系集合 → 学生数据零影响；而 DELETE 直接点燃级联 → 学生作答/错题/辅导记录当场消失且不可逆。

#### R-23（P0）：重导入会静默回退运营决策（status/kp_verified），且取消复核会再次触发缓存前提空洞

> 这条比 R-22 更隐蔽：即便工程师严格用了 `on_conflict_do_update`/`merge()`（满足 R-22），`merge()` 仍会**覆盖所有标量列**。而本期「规则大改后直接重跑导入」是**文档自己推荐的受支持操作**（Q5 修订版），于是埋下第二个雷。

| | 机制 | 单看是否正确 |
|---|---|---|
| A | upsert 命中同 PK 即整行 UPDATE（含 `status`/`kp_verified`） | ✅ ORM 幂等语义，理所当然 |
| B | 运营用 `promote_bank.py --promote` 把题 `archived→active`（决策 U2） | ✅ 正常上架流程 |
| C | 运营用 `--mark-verified` 把题 `kp_verified=false→true`（复核确认） | ✅ 正常复核流程 |
| D | 修订后 Q5 建议「规则大改后直接重跑导入」 | ✅ 合理的重灌 SOP |
| **A × B × C × D** | 重跑导入时，加载器若把 `status='archived'`、`kp_verified=False` 一起喂给 upsert，会静默把已上架题降级回 `archived`、把已复核题取消复核 | 🔴 运营决策被无声撤销 |

**两条具体危害**：

| 危害 | 后果 | 严重度 |
|---|---|---|
| ① 上架降级 | 已 `active` 的题被重导入 → `status` 被写回 `archived` → 该题从推荐池**静默消失**，运营毫无感知（无报错、无报告提示） | 高 |
| ② 复核回退 + 缓存空洞 | 已 `kp_verified=true` 的题被重导入 → `kp_verified` 被写回 `false` → 历史作答立刻不计入掌握度（CASE WHEN 置空）；而 `kp_verified` 翻转是**元数据变更**，`_is_cache_valid()` 感知不到（§7.2 缓存前提）→ 900s 内仍是旧值 → **与 R-21 同级的静默数据腐化** | **更高** |

**两条危害的共同根因（与 R-21 同源）**：又是**文档自身给出的操作建议有陷阱**——修订版 Q5 说"直接重跑导入会覆盖同 key 的题"，本意是刷新题干/答案，却没说"覆盖也会把运营的上架/复核标记一起覆盖掉"。

**产品要求（R-23 铁律）**：`on_conflict_do_update` 的 `set_` 列表**只包含源派生列**：`content` / `type_` / `options` / `section` / `source_doc` / `edition` / `source_type` / `correct_answer` / `analysis`（answers 表同理只更新 `correct_answer`/`analysis`/`distractor_analysis`）。**永不**在 `set_` 中出现 `status` / `kp_verified` / `kp_id` / `created_at`。⚠️ **不要用 `session.merge(全字段对象)` 来"省事"**：`merge` 会把对象上所有已设属性拷回持久行，等于把 `status='archived'`/`kp_verified=False` 一起写回，直接违反 R-23。必须用**显式 `on_conflict_do_update` + 受控 SET 列表**，不要依赖 merge 的属性拷贝细节。

> 📌 **与 OPS-3 互补**：OPS-3 管「`--reset-bank` 能做什么」（只能清从未练习的题），R-23 管「重导入能做什么」（只刷源派生列、保留运营决策）——两条操作路径都堵上了，根因同属"文档建议诱导破坏性操作"。

#### R-24（🟡）：`source_doc` 作全局键 × 文件名可能重名 → reset-bank / promote 串台

| | 机制 | 单看是否正确 |
|---|---|---|
| A | `source_doc` 一身三用：① 存量/新增判据（V7）② `--reset-bank` 删除键 ③ `--promote` 上架键 | ✅ 复用同一字段，简单 |
