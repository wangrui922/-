## 0. 项目信息

| 项 | 内容 |
|---|---|
| 项目名 | `epic6_parent_report`（家长周报告） |
| 所属产品 | AI 数学教练 V4（面向小学生的 AI 数学辅导） |
| 技术栈（沿用现有） | 后端 FastAPI + SQLAlchemy；前端 Vue3 + Vite + Tailwind（`student-web/`） |
| 战略定位 | **MVP 最小完成线的最后一块拼图**，做完即可找 20~100 名真实学生测试 |
| 原始需求 | 让家长能看到一份"孩子这周数学学得怎么样"的周报：学习时间 / 能力变化 / AI 建议 |

### 为什么是现在做

付费决策人是家长，孩子不掏钱。产品现在有 AI 讲题、错因诊断、能力画像，但**这些价值家长一次都没看到过**。周报是把已有的 E1~E5 能力"翻译"给家长看的唯一出口。

## 1. 产品目标

**一句话**：让家长花 60 秒读完一张卡片，就知道孩子这周数学练了多少、进步在哪、卡在哪、下周该练什么。

### 三条成功标准（正交）

| # | 目标 | 可衡量标准 |
|---|---|---|
| G1 | **看得懂** | 家长无需任何解释，能说出"孩子这周弱在哪一类"。测试口径：给 5 位真实家长看，≥4 位能正确复述孩子的主要错因类别 |
| G2 | **看得到** | 家长零注册、零下载、在微信里点开链接即可看。测试口径：分享链接在手机微信内打开成功率 100%，首屏可读时间 < 3 秒 |
| G3 | **信得过** | 报告里每个数字都能追溯到真实练习记录，不出现凭空编造的知识点与建议。测试口径：AI 建议中提及的知识点 100% 出现在孩子真实练习数据里；无数据时显示空态而非 0% |

### 非目标（本期明确不做）

- 不做家长注册 / 家长账号体系（V4.2 再补）
- 不做主动推送（微信模板消息 / 短信，需资质）
- 不做多科目，只做数学
- 不做家长与 AI 的双向对话

## 2. 用户故事

| # | 用户故事 | 优先级 |
|---|---|---|
| US-1 | 作为**家长**，我想在微信里点开一个链接就能看到孩子这周的数学学习情况，**这样**我不用注册账号也能了解孩子 | P0 |
| US-2 | 作为**家长**，我想一眼看到"这周练了多少、对了多少、新增几道错题、攻克几道"，**这样**我能判断孩子这周有没有真在学 | P0 |
| US-3 | 作为**家长**，我想知道孩子主要错在哪一类（读题错 / 方法错 / 计算错 / 知识点缺 / 检查漏），**这样**我不再只会说"你怎么这么粗心" | P0 |
| US-4 | 作为**家长**，我想看到一段人话写的建议告诉我"下周该让孩子练什么"，**这样**我有具体可执行的动作，而不是干着急 | P0 |
| US-5 | 作为**学生（或老师）**，我想一键生成周报并把链接发给家长，**这样**我的努力能被家长看见 | P0 |
| US-6 | 作为**家长**，我想看到孩子和上周比是进步了还是退步了，**这样**我能感知趋势而不只是单周快照 | P1 |

### 4.3 「能力变化」怎么算 —— 两条可落地路径

这是本期唯一的真实算法缺口，给架构师两个选项（推荐组合使用）：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 周报快照表**（推荐） | 生成周报时把当周 `mastery` 结果连同报告正文一起落一张 `weekly_reports` 表（本来就要做报告缓存，顺手存快照，边际成本≈0）。下周生成时读上周快照做 diff | 口径与能力地图完全一致；顺带解决 R-08 历史周报；一次投入长期受益 | **第一周没有对比基线** |
| **B. 窗口正确率对比**（首周兜底） | 直接对比「本周 attempts 正确率」与「上周 attempts 正确率」（按知识点或整体） | 第一周就有数字 | 与 mastery_score 口径不同（后者含时效衰减+贝叶斯平滑），两个数放一起会互相打脸 |

**产品建议**：主口径用 **A**；第一份周报显示「这是第一份周报，下周起可以看到变化对比 📈」，同时用 **B** 给一个整体正确率对比作为过渡。**不要**把 A 和 B 的数字并列展示。

### 4.4 接口与鉴权约束（给架构师的硬提示）

| # | 约束 | 依据 |
|---|---|---|
| C1 | **不能复用 `/api/profile/*` 的鉴权**。该模块的 `_require_student()` 强制 `role == "student"` 且 `sid` 非空，否则一律 403。家长是**未登录**访问，必须走独立的免鉴权只读路由 | `app/api/profile.py:46-65` |
| C2 | 分享页前端路由**必须标 `meta: { public: true }`**，否则会被 `router.beforeEach` 守卫弹去 `/login` | `student-web/src/router/index.ts` |
| C3 | 分享页**不能走 `api/http.ts` 的默认实例**（它会注入 Bearer token 并在 401 时强制跳登录），需单独的免鉴权请求通道 | `student-web/src/api/http.ts` |
| C4 | 响应外壳沿用 `{code, msg, data}`（`app/core/response.py`）。⚠️ **字段命名有冲突**：《迁移实施方案》D3 写的是 camelCase，但 `app/schemas/profile.py` 明确约定"T04 及之后的新接口统一 snake_case"。**建议按 snake_case**，与 profile / chat / exercise 对齐 | 见 Q5 |
| C5 | Report Agent 应复用现有大模型调用机制：`app/ai/ark_client.py` 的 `ark_respond(messages=[...], system=PROMPT)`，Prompt 单独放 `app/ai/prompts/report.py`，Agent 放 `app/ai/agents/reporter.py`，与 diagnose / exercise / tutor 保持同构 | `app/ai/agents/exercise.py` 可作模板 |
| C6 | 报告需缓存。现有掌握度缓存 TTL 是 900 秒（`MASTERY_CACHE_TTL_SECONDS`），周报缓存粒度应是"每学生每周期一份"，而非按秒过期 | `app/core/constants.py` |
| C7 | 计算失败时沿用画像模块的降级约定：**HTTP 仍返回 200**，body 里给 `code=5001` + 空壳数据，让页面画局部空态而不是整页崩 | `app/api/profile.py:98-112` |

## 5. UI 设计稿（FE-006）

### 5.1 设计原则

1. **移动端优先**：375px 起，家长 90% 在微信里看。桌面端居中限宽即可，不做两栏。
2. **一屏一件事**：三张卡片纵向排列，每张卡片独立可读，家长滑动阅读。
3. **说人话**：不出现"掌握度 0.62""EWMA""错因 CALC"这类词。全部翻译成中文标签与百分比。
4. **不吓唬家长**：弱项用中性词（"还需要多练"），不用红色警告风格堆满屏。

```
│         报告生成于 01-11 20:30           │      家长视角显示"更新于"
└─────────────────────────────────────────┘
```

### 5.3 分享链接落地页（家长视角，免登录）

与 5.2 主体完全一致，**差异只有三处**：

```
┌─────────────────────────────────────────┐
│  AI 数学教练 · 学习周报                  │   ← 极简品牌栏，无导航、无登录入口
├─────────────────────────────────────────┤
│                                         │
│        （卡片 ①②③ 与 5.2 完全相同）      │
│                                         │
├─────────────────────────────────────────┤
│  这份报告由 AI 数学教练自动生成           │
│  数据来自孩子 01-05 ~ 01-11 的真实练习     │   ← 建立信任
│         [ 了解 AI 数学教练 ]              │   ← 唯一转化入口(可选)
└─────────────────────────────────────────┘
```

1. **无左侧导航栏**：不复用 `StudentLayout.vue`，用独立的极简布局。
2. **无"分享"按钮**：家长不需要再分享（P1 可加"转发给另一位家长"）。
3. **底部有轻量转化位**：这是家长第一次接触产品，是最好的获客入口。

### 5.4 关键状态设计

| 状态 | 展示 |
|---|---|
| 本周无练习记录 | 整页空态："小明这周还没有练习记录～ 提醒他打开 AI 老师做两道题吧 😊"。**不显示任何 0% 数字** |
| 数据不足（练习 < 3 题） | 正常展示数字，但卡片②加提示："本周练习较少，能力判断仅供参考" |
| AI 生成失败 | 卡片③改用规则版建议（`recommendations[].reason`），**不显示任何报错**，家长无感知 |
| 链接失效 / token 非法 | 独立提示页："这个链接已失效，请让孩子重新生成一份" |
| 加载中 | 骨架屏，不用 loading 转圈（微信里白屏转圈体验差） |

## 6. 待确认问题（需老板拍板）

> 按重要性排序。**Q1、Q2 阻塞架构设计，请优先回复。**

### 🔴 Q1｜家长怎么访问报告：分享链接 vs 家长账号？

| 选项 | 工作量 | 优点 | 缺点 |
|---|---|---|---|
| **A. 分享链接（推荐）** | 约 3 小时 | 家长零门槛，微信里点开就看，转化路径最短；MVP 阶段验证"家长看不看"这个核心假设 | 链接可被转发（但报告本身不含敏感信息）；无法做多孩子切换 |
| B. 建 `parents` 表 + 家长账号 | 至少多 3 天 | 正规、可做多孩子、可推送 | 家长注册流失率高；MVP 阶段还没验证价值就先加门槛 |

**产品推荐：A**。理由：现在要验证的假设是"家长看到报告后会不会觉得有价值"，任何注册环节都会让这个验证失真。等验证通过（比如 20 位家长里有 15 位主动看了第二次），V4.2 再补正式家长端。

> 若选 A，还需确认：**链接有效期多久？** 建议 30 天（覆盖一个月的家长回看需求），过期后学生可重新生成。

---

### 🔴 Q2｜"学习时长"要不要做真实计时？

**现状（已核查）**：`attempts.duration_sec` 字段存在但**从来没有写入过**；`ai_sessions` 表没有结束时间字段。也就是说，**现在拿不到任何真实时长数据**。

| 选项 | 工作量 | 说明 |
|---|---|---|
| **A. 本期不显示"时长"，改用"学习天数 + 题数 + 辅导次数"（推荐）** | 0 | 这三个数据 100% 真实可查。对家长来说"这周学了 4 天、练了 32 题"比"学习 87 分钟"更有说服力，也不会被质疑 |
| B. 前端埋点真实计时，补写 `duration_sec` | 约 1 天 | 需前端记录答题起止、后端接收字段、还要处理"孩子开着页面去吃饭"的脏数据 |
| C. 用会话数 × 固定系数估算 | 0.5 小时 | **强烈不建议**：编造数字，一旦家长发现就是信任崩塌，直接违背 G3 |

**产品推荐：A**。周报里"学习时间"这一栏改叫**"本周学习投入"**，展示学习天数 / 练习题数 / 辅导次数三个真数。真实计时留到 V4.2 和"专注力分析"一起做。

---

### 🟡 Q3｜报告怎么触发生成？

| 选项 | 说明 |
|---|---|
| **A. 按需生成（推荐）** | 学生/老师点"生成周报"按钮 → 后端聚合 + 调 AI → 出报告 + 分享链接。同一周期内重复点走缓存，不重复烧 token |
| B. 后台定时任务每周一自动生成 | 需引入 APScheduler，且没人看的报告也会烧 AI 费用 |

**产品推荐：A**。MVP 阶段用户量小，按需生成足够，且能省下大量无人查看的 AI 调用成本。定时推送已排在 P2（R-13）。

> 若选 A，需确认：**入口放哪里？** 建议放在学生端「学习画像」页（`/dashboard`）顶部加一个「生成家长周报」按钮，因为那里本来就是看数据的地方。

---

### 🟡 Q4｜报告周期粒度用哪个？

| 选项 | 说明 |
|---|---|
| **A. 自然周，周一 00:00 ~ 周日 23:59（推荐）** | 符合家长心智（"这周"），周报名字也叫得顺；缺点是周三生成时只有半周数据 |
| B. 滚动 7 天（生成时刻往前推 7×24 小时） | 数据量恒定，但家长不好理解"这是哪一周" |

**产品推荐：A**，并在标题明确标出日期范围（如 `2026-01-05 ~ 2026-01-11`）。若在本周中途生成，加一行小字"本周还没结束，数据统计到今天"。P1 阶段（R-09）再加"近 30 天"选项。

### 🟢 Q5｜接口字段命名用 camelCase 还是 snake_case？

**冲突点**：《迁移实施方案》D3 写的是 camelCase，但 `app/schemas/profile.py` 里明确写着"T04 及之后的新接口统一 snake_case，与 /api/chat、/api/exercise 对齐"。

**产品推荐：snake_case**。理由：周报要大量复用 profile 的现成数据结构（`error_patterns`、`mastery` 等），若换成 camelCase，前端得写一层字段转换，`ErrorPatternChart.vue` 也无法零改造复用，白白多出工作量和 bug 面。

---

### 🟢 Q6｜"能力变化"第一周没有基线，怎么呈现？

见 §4.3。**产品推荐**：主口径用「周报快照表」（方案 A），第一份周报显示"这是第一份周报，下周起可以看到进步对比 📈"，同时用整体正确率对比（方案 B）做过渡。请确认是否接受"第一周看不到完整变化对比"。
