## 0. 现状核实与关键更正（先读这一节）

我读了代码，有 **4 处与任务书描述不一致**，直接影响实现方案，请以本节为准。

### 0.1 字段名不是 `knowledge_point_id`，是 `kp_id`

`Question` 的知识点外键实际叫 **`kp_id`**（`app/models/content.py:110`），FK → `knowledge_points.id`，`nullable=True`，带索引。
配套的 `kp_verified`（`BOOLEAN NOT NULL DEFAULT 1`）语义是：**存量题默认视为已复核（1）**，docx 导入器写新题时显式传 `0`——与任务书说的「默认 false」相反。见 `migrations/004_bank_columns_sqlite.sql`。

### 0.2 迁移方式不是 Alembic，是编号裸 SQL（双方言）

项目**没有 Alembic**（`models/__init__.py` 的 docstring 提了一嘴，但目录里没有）。实际约定是 `backend/migrations/` 下的编号 SQL，PG 与 SQLite 各一份：

```
001_init.sql / 001_init_sqlite.sql
002_question_status.sql
003_weekly_reports.sql / 003_weekly_reports_sqlite.sql
004_bank_columns.sql   / 004_bank_columns_sqlite.sql
```

另有运行时列探测兜底 `app/services/importers/schema_guard.py::ensure_bank_columns()`（SQLite 的 `ADD COLUMN` 不支持 `IF NOT EXISTS`，靠先探测规避重复执行报错）。
→ **本次应新增 `005_mistake_kp.sql` + `005_mistake_kp_sqlite.sql`，并沿用 `schema_guard` 的探测模式。** 开放问题 Q2 不再是问题。

### 0.3 ⚠️ 最关键：知识点树只有 13 个扁平粗粒度节点

`backend/seed/knowledge_points.json` 全量如下，**无任何父子层级**（`parent_id` 引用数为 0），无年级维度：

```
计算 / 方程 / 应用题 / 分数 / 小数 / 百分数 / 比例
几何 / 图形 / 统计 / 单位换算 / 数论 / 综合
```

这意味着：**B 的管道即使全部打通，产品价值也会大打折扣**。一道三年级的错题挂在「计算」上，点「练同类题」会抽到 1–6 年级所有计算题；挂在「综合」上基本等于没挂。
**真正的瓶颈是知识点树太粗，不是抽取算法不够强。** 处理方案见 P0-3 与 Q1。

### 0.4 Jiagu 不适合当知识点分类器（建议降级使用）

Jiagu 是通用领域中文 NLP 库（分词 / 词性 / NER / 关键词 / 文本聚类 / 关系抽取），其「知识图谱关系抽取」训练于通用三元组（人物-地点-机构），**与 K12 数学知识点体系无对应关系**。用它做「题干 → 数学知识点」分类属于用途错配。

而且——**要匹配的只有 13 个粗粒度桶**。这是一个关键词词典就能做到高准确率的任务，上 NLP 关系抽取属于杀鸡用牛刀。

→ 建议：**Jiagu 降级为分词 / 关键词抽取的预处理助手**（可选依赖，非必需），分类决策主体用「人工同义词词典 + 规则」，低置信度回退方舟。详见 P0-2。
（此更正与 MindSpore/course 那条同类：先证伪前提，再定方案。）

### 0.5 前端深链的「另一半」已经建好了

`RecommendationList.vue`（家长画像页）已实现同款深链：emit `{ kp_id, kp_name }`（snake_case 直传，不转驼峰）→ `Practice.vue:295` 读 `route.query.kp_id / kp_name` → `startDeepLink()` **直接开练**（不停在筛选态）。
`/api/practice/session` 也**已支持 `kp_id` 入参**（`app/api/practice.py:70`），抽题池逻辑 `practice_service._candidates` 已有「可归因池（`kp_verified=1 AND kp_id IS NOT NULL`）→ 数量不够自动放开到全 L1 安全池 → 回避最近 7 天做过的题」三级回退。

→ **B 的前端与抽题侧几乎零新增，只需在错题本复用现成模式。** 真正缺的只有「错题拿不到 kp_id」这一环。
`Mistakes.vue:122-130` 的注释已把这个断点写得很清楚（后端无 `kp_id` 列 + `_to_item()` 不吐 kp），可作为验收对照。

## 1. 产品目标

**一句话**：让每一道错题都能一键跳到「同知识点的针对性练习」，并让 `/guide` 的追问更像真老师——把「看懂错题」真正接到「会做同类题」。

拆解为三个正交目标：

1. **数据可归因**：错题必须携带知识点归属，让「错题 → 练习 → 掌握度」形成闭环（当前断点）。
2. **跳转有价值**：跳过去抽到的题要真的相关，而不是同一个粗桶里的随机题。
3. **引导有章法**：`/guide` 的追问节奏、给提示/沉默的时机、不同错因的话术差异，从「靠模型自由发挥」变成「有明确清单约束」。

## 2. 用户故事

### B · 错题 → 知识点深链

- **US-B1**：作为**学生**，我在错题本看到一道做错的题时，想直接点「练同类题」，这样我不用自己去筛选页猜该选哪个知识点。
- **US-B2**：作为**学生**，我点进去练的题应该和我错的那道**同知识点、同年级档**，这样我才觉得这是在补我的短板，而不是随机刷题。
- **US-B3**：作为**家长**，我想在错题卡片上看到这道题属于哪个知识点，这样我能判断孩子是某个板块整体薄弱，还是只是偶尔失误。

### C · `/guide` 引导优化

- **US-C1**：作为**学生**，我卡住时希望老师一步步问、每次只问一件事，而不是一次丢给我一大段讲解，这样我跟得上。
- **US-C2**：作为**学生**，我只是算错了一个数的时候，希望老师直接陪我查那一步，而不是从「这题求什么」重新问一遍，这样我不觉得被当傻子。
- **US-C3**：作为**产品/教研**，我希望「什么时候给提示、什么时候沉默让孩子自己想」有成文规则和可回归的用例，这样改提示词不靠玄学，出问题能定位。

**验收**：`Mistakes.vue:122-130` 那段「做不了知识点直达」的注释可以被删掉。

#### P0-2 知识点自动归因（填补 `Question.kp_id` 为空的题）

**方案（三级，按序尝试，非 Jiagu 主导）**：

1. **规则词典（主力）**：人工维护 `kp_keywords.json`，为 13 个知识点各配同义词/特征词（如 `分数` ← 分子/分母/约分/通分/几分之几；`单位换算` ← 千米/千克/平方米/时分秒 + 「=」「合计」）。命中唯一 → 直接落 `kp_id`，`kp_verified=0`。⚠️ 注：实际 `kp_keywords.json` 当前**不含「=」关键词**——若未来补「=」，会命中几乎所有含等号的填空题，风险比「合」更高，需配套样本验证后再加。
2. **Jiagu 辅助（可选依赖，非必需）**：仅用其**分词 + TextRank 关键词抽取**，把题干切成候选词再喂给第 1 步词典，提升长应用题的召回。**不使用其关系抽取/知识图谱能力**（理由见 0.4）。若引入需加入 `requirements.txt`（当前无此依赖），并确认离线可用、模型体积与启动耗时可接受。
3. **方舟兜底**：前两级未命中或命中多个桶（置信度低）→ 调 `ark_respond`，给定 13 个知识点封闭选项做单选分类，落 `kp_id` + `kp_verified=0`。

**兜底与安全**：
- 任何自动归因结果一律 `kp_verified=0`（未复核），**不污染现有可归因池**——`_candidates` 的可归因池条件是 `kp_verified=1 AND kp_id IS NOT NULL`，所以自动归因的题默认只进「放开后的全 L1 安全池」，不会挤掉人工确认过的题。
- 三级全部失败 → `kp_id` 留空，走现有回退路径，不阻塞。
- 以**离线批处理脚本**运行（`app/scripts/backfill_kp.py`），支持 `--dry-run` 输出归因分布供人工抽检，**不在请求链路里跑 NLP**。

#### P0-3 深链带 `grade` 收窄（对 0.3 粗粒度问题的止血）

在知识点树细化落地前（Q1 待定），深链**必须同时携带错题所属题目的 `grade`**：
`{ kp_id, kp_name, grade }` → `/api/practice/session`（`DrawParams` 已支持 `grade` / `difficulty` / `kp_id`，无需改接口）。
效果：「三年级 × 计算」远好于「全学段 × 计算」，成本几乎为零。

### P1 · C：`/guide` 引导逻辑优化

> **不改架构，只产出文档 + 提示词 patch 建议。**

#### P1-1 先澄清：`/guide` 用的不是 tutor 提示词

任务书说 `/guide` 是「让老师带我想」主按钮走 Socratic 引导，实际是两套提示词：

| 入口 | 提示词 | 说明 |
| --- | --- | --- |
| `POST /api/practice/guide` | `app/ai/prompts/practice_guide.py`（v1.0.0，占位符 `{{QUESTION}}` `{{WORK}}`，返回 `{"reply","askFinalConfirm"}`） | **本次优化目标**，35 行，相对简略 |
| AiTeacher 对话 | `app/ai/prompts/tutor.py`（v1.0.0，63 行） | 已含完整【错误诊断】【引导的拿法】【内部状态判断】 |

**结论：`tutor.py` 里已经沉淀了成熟的教学法资产，`practice_guide.py` 明显偏薄。C 的本质是把 tutor 的教学法下沉/裁剪到 practice_guide，而不是从零发明。**

#### P1-2 交付物：《`/guide` 追问逻辑优化清单》

独立文档 `docs/guide-prompt-optimization.md`，含：

1. **分步追问节奏**：每轮 1 个问题上限（tutor 铁律 2 已有，practice_guide 缺）；每轮 2–4 句；连续 2 轮无进展 → 降一级颗粒度拆小问题。
2. **给提示 vs 沉默的判定表**：孩子「在写中间步骤」→ 只肯定不推进（沉默倾向）；「明确说不会」→ 给轻提示；「方向错」→ 抛矛盾问题不纠正；「已完整」→ 问最终确认（现有 `askFinalConfirm` 已支持）。
3. **错因类型 × 话术差异**：直接复用 `tutor.py` 已有的五分类，**统一为项目术语**——
   `读题错`（不知求什么）/ `方法错`（运算选错）/ `计算错`（方法对算错）/ `知识点缺`（公式不会）/ `检查漏`（思路对漏一步）。
   每类给 2–3 条示例话术与反例。
4. **提示词 patch 建议**：以 diff 形式给出 `practice_guide.py` 的建议改动，**升 `VERSION` 到 1.1.0**（该文件与 `tutor.py` 都注明「改动需评审并升版本」）。
5. **回归用例**：≥10 条（题干 + 孩子作答 + 期望引导行为），至少覆盖 5 类错因各 1 条 + 泄题红线 2 条。

#### P1-3 保留现有代码层兜底

`practice_service.guide_question` 的 `judge_engine.leaks_answer()` 复核 + `GUIDE_FALLBACK_REPLY` 兜底**必须保留**。提示词改动后需重跑泄题回归——提示词是软约束，代码闸门是硬约束，不能互相替代。

### 4.2 跳转行为

点 `[练同类题 →]`：

```
Mistakes.vue
  └─ router.push({ name: 'practice',
                   query: { kp_id, kp_name, grade } })   ← snake_case 直传
       └─ Practice.vue onMounted 读 route.query
            └─ startDeepLink() → 直接开练（不停在筛选态）
                 └─ POST /api/practice/session { kp_id, grade, count }
```

- **与画像页「练这个」完全一致的行为**：读到 `kp_id` 就直接开练，不让孩子在筛选页再点一次。
- `grade` 为新增第三参，`Practice.vue` 的 query 解析需相应扩展（现只读 `kp_id` / `kp_name`）。
- 练习页顶部显示来源提示：**「正在练：计算（来自你的错题）」**，让孩子知道这不是随机题。
- 抽题不足时沿用现有三级回退，**但 UI 需提示已放宽条件**，避免孩子以为系统给错了题。

## 6. 依赖与边界声明

### 明确依赖

- **B 依赖「现有题库已有知识点字段可作对齐基准」**——成立，但请注意实际字段名是 **`Question.kp_id`**（非 `knowledge_point_id`），对齐基准是 `knowledge_points` 表的 **13 个 `code`**（`KP_CALC` / `KP_FRACTION` / …），自动归因的输出必须落在这个封闭集合内，不得自造新知识点。
- **B 依赖 P0-1 先于 P0-2 完成**（先有列，再回填）。
- **B 的前端依赖 `Practice.vue` 的 query 深链能力**——已存在，仅需扩展 `grade` 参数。

### 明确边界（不做）

- **C 不改架构**：不动路由、不动 `{"reply","askFinalConfirm"}` 契约、不动 `PracticeGuideDrawer.vue`、不动 `judge_engine.leaks_answer()` 闸门。**只产出文档 + 提示词 patch 建议**，提示词是否合入由负责人评审后决定。
- **不使用 DeepSeek**，所有 AI 调用统一走 `ark_respond`。
- **不引入 Alembic**，沿用编号裸 SQL 双方言 + `schema_guard` 探测。
- **不改 `/api/mistake/*` 的 camelCase 出参风格**（T03 既有接口约定）。
- **不在请求链路里跑 NLP**，自动归因一律离线批处理。

### 交付顺序建议

```
P0-1（迁移 + 出参）→ P0-4（前端入口，此时已可深链）
       ↓
P0-2（自动归因批处理）→ 提升深链覆盖率
       ↓
P0-3（grade 收窄）可与 P0-4 同期
       ↓
P1（/guide 文档 + patch，与 B 无耦合，可并行）
```

P0-1 + P0-4 完成即可交付一个**可感知的闭环**（对已有 kp 的题生效）；P0-2 是覆盖率放大器，不阻塞首次交付。
